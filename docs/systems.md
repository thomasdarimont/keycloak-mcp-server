# Several Keycloak systems

[keycloak-mcp-server](../README.md) › documentation

One server for several Keycloak installations: configured statically, supplied by a repository at runtime, or registered through the admin API; per-system keys; one MCP entry per system or realm.

Every Keycloak the server administers is a named system, `kc-mcp.systems.<name>.*`; a system exists exactly when
its `url` is set, and a blank `url` switches a configured one off. There is no unnamed system: one Keycloak is
usually called `default`, a name like any other. Settings a system leaves out come from `kc-mcp.system-defaults.*` (the same keys except
`url`), then from the built-in defaults.

```properties
kc-mcp.system-defaults.grant-type=client_credentials
kc-mcp.system-defaults.client-id=mcp-admin
kc-mcp.systems.prod.url=https://sso.example.com
kc-mcp.systems.prod.client-secret=${PROD_SECRET}
kc-mcp.systems.prod.allowed-realms=customers,partners
kc-mcp.systems.staging.url=https://sso-staging.example.com
kc-mcp.systems.staging.client-secret=${STAGING_SECRET}
kc-mcp.default-system=prod
```

- More than one system: every tool gains a `system` argument (enum; optional with a default system).
- The default system: `kc-mcp.default-system`, else the only system. Several systems without the setting have no
  default, and every tool requires `system`; a system called `default` is not picked by its name. The OIDC default
  tenant verifies callers against the default system's auth realm (`quarkus.oidc.auth-server-url` is derived from it
  unless set): with caller login, several static systems need `kc-mcp.default-system` or
  `quarkus.oidc.auth-server-url`, or the server does not start.
- Roles, allowed realms, default realm, startup checks, audit: per system.
- One `kc-mcp.jwt.key-file` serves all systems; without it each system gets its own key (see Dynamic systems below).
- Environment form: `KC_MCP_SYSTEMS_PROD_URL`, `KC_MCP_SYSTEM_DEFAULTS_CLIENT_ID`; a system name given through the
  environment is lower-case letters and digits.
- One file per system: the distribution reads every `*.conf` file of a directory given to `--config`
  (`kc-mcp.config-files`), so `conf/systems/prod.conf`, `conf/systems/staging.conf` and so on each hold
  their system's `kc-mcp.systems.<name>.*` settings, and the shared ones stay in `conf/kcmcp.conf`
  ([Configuration](configuration.md)).

## Dynamic systems and per-system keys

`KeycloakSystemRepository` extensions (`@AutoService` or CDI bean) supply systems at runtime: `names()`, `find(name)`.

- Off by default: `kc-mcp.dynamic-systems=true` enables repositories, `kc-mcp.spi.<spi>.<id>.enabled` one of them. Found
  while off: only logged.
- The server creates nothing in Keycloak; the tenant registers the client, the server keeps its key.
- `CompositeKeycloakSystemRepository` asks repositories by `order()`. Static configuration sits at
  `kc-mcp.static-systems-order` (-1000): repositories cannot redefine configured systems unless that is raised. First
  repository knowing a name wins; admin client created on first use, cached per name; changed settings reconnect,
  forgotten systems drop.
- Schema of the `system` argument: a closed enum of the configured names without repositories; with one, a plain string
  (systems may appear at runtime), known names listed in the description as examples, unknown names answer `unknown_system`.
- `kc-mcp.allowed-hosts` still applies: outside systems are refused and logged, not fatal; so does
  `kc-mcp.dynamic-private-hosts` ([Guardrails](security.md#guardrails)).

Credentials by convention, no secret per tenant:

- Each system registers a confidential client (e.g. `keycloak-mcp-server`): service account, "Signed JWT", JWKS URL
  `https://<this server>/auth/keys/<key set>/jwks.json`, the `realm-management` roles needed.
- The server signs with a key pair per system from a `KeyVault`, publishes the public half at that URL.
- The key set is a stored system's id when the vault creates keys, else the system's name (provisioned
  `<alias>.pem`). Deleting a stored system removes its keys, so its JWKS answers 404; a new system of the same name
  gets another id, key and URL and inherits none of the trust Keycloak placed in the old one. The client in Keycloak
  stays until it is deleted there.
- Built-in vault: read-only PKCS#8 PEM files under `kc-mcp.keys-dir` (default `data/keys`, next to `quarkus-run.jar`
  when packaged): `<system>.pem`, secrets as `secrets/<name>` files.
- Own `KeyVault`: `findSigningKey`, `createSigningKey` when `supportsKeyCreation()`, `findSecret`, `putSecret` when
  `supportsSecretStorage()`. Keys generated by the `SigningKeyGenerator` the server hands over (JDK RSA/EC for
  `kc-mcp.jwt.algorithm`, RSA size `kc-mcp.jwt.key-size`; own one for an HSM). Or a secrets manager such as HashiCorp
  Vault: the server handles references only.
- `kc-mcp.jwt.key-file` keeps one key for all systems, also at `/.well-known/jwks.json`.
- `FileSystemKeycloakSystemRepository` reads `kc-mcp.systems-file` (re-read on change). `kc-mcp.static-systems=false`:
  repositories only. `examples/multi-tenant/`: two tenants, provisioned keys, one entry per tenant. Database: [Database storage](storage.md).

```json
{ "systems": [
  { "name": "tenant-a", "url": "http://keycloak:8080", "authRealm": "tenant-a",
    "clientId": "keycloak-mcp-server", "clientAuth": "private_key_jwt",
    "defaultRealm": "tenant-a", "allowedRealms": ["tenant-a"] } ] }
```

An own repository, for example over a tenant registry:

```java
@AutoService(KeycloakSystemRepository.class)
public class TenantRegistryRepository implements KeycloakSystemRepository {
    public String id() { return "tenant-registry"; }
    public List<String> names() { return registry.tenantIds(); }
    public Optional<KeycloakSystem> find(String name) {
        return registry.lookup(name).map(t -> KeycloakSystem.builder(name, t.keycloakUrl())
                .clientId("keycloak-mcp-server").defaultRealm(t.realm()).allowedRealm(t.realm()).build());
    }
}
```

## Admin API: registering systems at runtime

Needs database storage and `kc-mcp.admin.enabled=true`. JAX-RS under `/admin`. Full flow: `examples/dynamic-systems/`.
It can run on an instance of its own, with the MCP endpoint off there (`kc-mcp.mcp.enabled=false`), next to the MCP-facing
instances on the same database ([Several instances](storage.md#several-instances-on-one-database)).

- Bearer, preferably an access token of `kc-mcp.admin.issuer` (a realm URL, verified by Quarkus OIDC, optional
  `kc-mcp.admin.audience`) carrying `kc-mcp.admin.role` (`realm:admin` default; `<client>.<role>` for client roles): a
  person's token from the authorization code flow, or a service account's from the client credentials grant, so Keycloak
  governs who administers the server, with expiry and revocation. The static `kc-mcp.admin.token` is the alternative for
  bootstrapping and simple automation; it never expires and is only as safe as the file or variable holding it. One of
  issuer and token is required. Only tokens of the admin issuer count: without `kc-mcp.admin.issuer` the API takes the
  static token alone, and an MCP caller's access token is refused whatever roles it carries.
- `PUT /admin/systems/<alias>`: systems file fields (`displayName`, `description`, `url`, `issuer`, `authRealm`,
  `clientId`, `clientAuth`, `defaultRealm`, `allowedRealms`, `trustedIssuers`, `version`, `clientSecret`,
  `access`, `tools`, `preset`, `presets` ([Access checks](access-checks.md))) into the first
  `MutableKeycloakSystemRepository`. Registered systems are service clients: `client_credentials` with
  `private_key_jwt` or `client_secret`; `grantType: password` answers 400 `grant_not_supported`.
  `url` must pass `kc-mcp.allowed-hosts`. `kc-mcp.admin.allow-new-systems=false` freezes the set: unknown aliases answer
  403 `registration_closed`, known systems stay changeable (reading stored systems only needs `kc-mcp.dynamic-systems`,
  not the admin API).
- `GET|PUT|DELETE /admin/systems/<alias>/realms/<realm>`, `GET /admin/systems/<alias>/realms`: the settings of single
  realms of a registered system: `realmId` (Keycloak's id of the realm), `displayName`, `description`, and an
  `preset`, `access` and `tools` over the system's ([Presets](access-checks.md#presets)). A system's own `PUT` carries
  no `realms` (400 `realms_separately`) and keeps them; `DELETE` of the system removes them.
- `signingKey`: `generate` (new pair in a creating vault), `existing` (vault already has one), absent (existing, else generate).
- `"clientSecret": "vault:<name>"`: checked on registration, resolved on every connection; rotating the secret needs no
  system change.
- Response: no secrets; `kid`, `jwksPath` (`/auth/keys/<id>/jwks.json`), `jwksUrl`, entries, `createdAt` /
  `updatedAt` (ISO-8601, from repositories that keep them: the database, not the static configuration).
- `GET /admin/systems[/<alias>]`: all systems with `source` repository (configured ones read-only). `DELETE`: removes a
  registered system, keys stay. `POST /admin/systems/<alias>/signing-key`: rotates; JWKS lists the new key first, keeps
  the retired one for the grace period; Keycloak refetches on unknown `kid`.
- `PUT /admin/secrets/<name>` `{"value": "..."}`: stores a secret in the database vault (file vault, secrets manager:
  409 `vault_read_only`). Systems with `vault:<name>` pick it up on their next connection. `GET /admin/secrets[/<name>]`:
  names + `usedBy`, never values. `DELETE`: 409 `secret_in_use` while referenced.
- `GET /admin/storage`: encryption on/off, current key id, key ids in use per table. `POST /admin/storage/rekey`:
  re-encrypts under the current `kc-mcp.storage.secret-key` ([Database storage](storage.md), key rotation).
- `GET /admin/audit`: the audit trail, newest first, 50 events a page (`limit` up to 500). Filters, combined with AND:
  `subject` (token `sub`), `caller` (name), `system`, `realm`, `tool`, `level` (`READ`, `WRITE`, `DESTRUCTIVE`),
  `outcome` (`ok`, `error` for every refusal and failure, or one error code), `from` / `to` (ISO-8601, `to`
  exclusive), `traceId` (the OpenTelemetry trace of the call), `anonymous=only` or `exclude` (calls without, or only with, a caller). `sort=when|took|caller` with
  `order=asc|desc` orders by time (the default, newest first), duration or caller name. An event says whether it has arguments (`hasArgs`); the
  arguments themselves come with `args=true`, or one event at a time from `GET /admin/audit/<id>`, since they may hold
  personal data. `next` in the answer is the `cursor` of the following page; new events do not shift the pages. `total`
  counts the matching events on all pages. `GET /admin/audit/values/{caller|system|realm|tool}?containing=`: up to 20
  recorded values containing a text, for completing the filters. The CIBA number-matching code never reaches the trail
  (it travels in `approval.code`, not the message); rows of older builds show it as `**`. 503
  `storage_disabled` without the database storage ([Audit retention and personal data](storage.md#audit-retention-and-personal-data)).
- `GET /admin/extensions`: every installed extension (`spi`, `id`, status, origin, class, whether it declares
  settings, how many errors and warnings its settings have). `GET /admin/extensions/<spi>/<id>`: its settings, read
  only: each declared setting with its full key and environment variable, type, default, options, conditions
  (`appliesWhen`), whether it is set and its value (confidential ones `******`), the groups, the keys the server
  handles itself (`enabled`, `required`, ...), undeclared keys (values always masked) and the problems the startup
  checks see, with code, named args and message. Labels, descriptions and messages are in the language of
  `Accept-Language`, English where no bundle has it, each with its message key ([Extending](extending.md),
  `configSpec()`).
- **OpenAPI.** The server serves the API's description at `/q/openapi` (YAML; `?format=json`), with every operation,
  the request and response schemas and the error codes; the source is
  `modules/backend/src/main/resources/META-INF/openapi.yaml`, kept in step with the resource by a test. Swagger UI
  browses it at `/q/swagger-ui`, in the packaged server too. Its *Authorize* dialog offers what this server is
  configured for: the static token, and the trusted issuer's login by OpenID Connect discovery (a public client of that
  realm with the redirect URI `<server>/q/swagger-ui/oauth2-redirect.html`, PKCE); with the API off it offers nothing
  and the document says so. Both are served whether the API is on or not; `kc-mcp.admin.openapi=false` takes them off
  the server (404).

### Walkthrough: a new system with `private_key_jwt`

No shared secret changes hands: the server signs its token requests with a key pair of its own, and Keycloak fetches
the public key from a JWKS the server publishes per system. `examples/dynamic-systems/` runs this end to end.

1. **Server side.** Dynamic systems and the admin API are on, with the database storage holding systems and keys:
   `kc-mcp.dynamic-systems=true`, `kc-mcp.admin.enabled=true` with `kc-mcp.admin.token` or an admin issuer,
   `quarkus.datasource.jdbc.url` and `kc-mcp.storage.secret-key`. The Keycloak's host must pass `kc-mcp.allowed-hosts`.
2. **Register the system** and let the server generate its key:

   ```shell
   curl -s -X PUT https://mcp.example.com/admin/systems/acme \
     -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
     -d '{ "displayName": "ACME", "url": "https://sso.acme.example", "authRealm": "master",
           "clientId": "keycloak-mcp-server", "clientAuth": "private_key_jwt",
           "defaultRealm": "acme", "allowedRealms": ["acme"], "signingKey": "generate" }'
   ```

   The answer carries no secret: `signingKey.kid`, `signingKey.jwksPath` (`/auth/keys/<id>/jwks.json`) and
   `signingKey.jwksUrl`, the full URL as the caller reached the server, so an internal hostname needs
   `X-Forwarded-Proto` and `X-Forwarded-Host` from the proxy to come out right. The JWKS is public and lists the
   current key, after a rotation also the retired one for the grace period.
3. **Client in Keycloak**, in the realm named as `authRealm`: a confidential client `keycloak-mcp-server` with
   *Service accounts roles* on and the `realm-management` roles (or master `admin`) it needs; under *Credentials*
   choose *Signed JWT*, switch *Use JWKS URL* on and enter `jwksUrl` from the answer (`https://mcp.example.com/auth/keys/<id>/jwks.json`). On
   Keycloak 26.8.2 and later add the client scope `kc-admin-api` as a default scope. Keycloak fetches the key on the
   first token request and again whenever it meets an unknown `kid`.
4. **Check.** `GET /admin/systems/acme` shows the system with `source: db`; a call to
   `/mcp/systems/acme` (`whoami`) runs as the new service account. A failing token request answers
   `keycloak_unreachable` or `unauthorized` with the Keycloak error: `invalid_client` usually means the JWKS URL is
   not reachable from Keycloak or the `kid` is unknown, `Invalid token audience` that `issuer` is wrong or missing:
   it is the auth realm's issuer (`https://sso.example.com/realms/master`, not the base URL; a save refuses anything
   else with `invalid_issuer`), needed only when the server reaches Keycloak at an internal URL.
5. **Rotate** with `POST /admin/systems/acme/signing-key`: the JWKS lists the new key first and keeps the retired one
   for `kc-mcp.spi.key-vault.db.retired-key-grace-seconds`, so Keycloak switches without a gap.

### Adopting a Keycloak's realms

Register the system first (step 2 above), then:

- `GET /admin/systems/<alias>/client-setup[?roles=admin|read|manage&realms=a,b&credential=jwks-url|public-key]`: the
  client for the system's `authRealm` as JSON (`POST /admin/realms/<realm>/clients`), the roles of its service account
  and a `kcadm.sh` script doing both (role and role scope; full scope is off). The server creates nothing in Keycloak.
  - `roles=admin` (default): master's `admin` role, every realm, later ones too, incl. creating realms;
    `read` / `manage`: view/query (and manage) roles of the `<realm>-realm` clients of `realms` only. Outside master:
    `realm-management` roles of that realm.
  - `credential=public-key`: the current key copied into the client (`jwt.credential.public.key`), for a Keycloak that
    cannot reach the JWKS URL; a rotation needs a client update.
- `GET /admin/systems/<alias>/keycloak-realms`: `GET /admin/realms` with the system's credentials, i.e. the realms the
  account may see, with `adopted` (settings kept), `allowed` (reachable), `renamedFrom` (same realm id under another
  name); `notListed`: known here, not listed there. Keycloak failures answer 502: `token_refused`,
  `admin_api_unauthorized` (kc-admin-api scope), `admin_api_forbidden` (roles), `keycloak_unreachable`.
- `POST /admin/systems/<alias>/adoption` `{"realms": [...], "restrict": true, "preset": "read-only"}`: realm id and
  display name become realm settings (`preset` for new ones), the realms go on the allowlist. Existing settings keep
  theirs, gain the realm id. On a system without an allowlist a selection restricts it: 409 `would_restrict` without
  `restrict: true`. `{"allRealms": true}`: every listed realm, allowlist cleared (later realms reachable).
- `DELETE /admin/systems/<alias>/adoption/<realm>[?restrict=true]`: gives a realm up. It leaves the allowlist (the
  access ends) and its realm settings go; Keycloak keeps the client and its roles. Without an allowlist the system
  reaches every realm, so leaving one out makes the allowlist the other listed realms: 409 `would_restrict` without
  `restrict=true`. Refused: the last realm on the allowlist (`last_realm`, an empty allowlist means every realm) and
  the default realm (`default_realm`).
- UI: system → **Adopt** tab, the same steps; **Unadopt** on an adopted or allowed realm.

Without the database, the systems file does the same with a provisioned key: the entry in `kc-mcp.systems-file`
names `"clientAuth": "private_key_jwt"`, the private key lies in `kc-mcp.keys-dir` as `<alias>.pem` (PKCS#8 PEM), and
the JWKS of that key is served at `/auth/keys/<alias>/jwks.json`: a provisioned key goes by the name. `examples/multi-tenant/` provisions keys
this way.

Caller authentication is per MCP entry, not per system: one login per server URL. Several systems: one central identity
(master admin), or one entry per system (next section).

## Entries per system or realm: `/mcp/systems/<system>[/<realm>]`

Same server, bound to one system or realm.

- `system` and `realm` arguments filled from the entry; contradicting arguments: `entry_mismatch`.
- `search_tools` and `whoami` judge roles and capabilities against that system; `whoami` reports `entry`.
- Global tools ignore the realm part.
- With OIDC on, entry requests are verified against the system's auth realm (`<url>/realms/<auth-realm>`): tenant A's
  users log in at tenant A's Keycloak; forward delegation works across systems. Systems sharing the default tenant's
  realm keep the default tenant.
- Each such entry has its own protected resource metadata, at the well-known path plus the entry's path:
  `/mcp/systems/acme` answers 401 with `resource_metadata="…/.well-known/oauth-protected-resource/mcp/systems/acme"`,
  and that document names the system's realm as the authorization server (`/mcp/systems/acme/sales` likewise, under
  `…/mcp/systems/acme/sales`). An entry on the default tenant's realm shares the root document
  `/.well-known/oauth-protected-resource`. MCP clients follow the link from the 401, so they log in at the right realm
  without further configuration.
- Unknown system: `unknown_system` on every call. `/mcp/*` permission policy covers entries.
- In delegation mode a caller's token never crosses to another Keycloak: a call that names a system whose Keycloak
  did not issue the token answers `caller_foreign_system` ([Security](security.md#callers)).

```json
{ "mcpServers": {
    "keycloak-prod":      { "url": "https://mcp.example.com/mcp/systems/prod" },
    "keycloak-customers": { "url": "https://mcp.example.com/mcp/systems/prod/customers" } } }
```

Support desk: realm entry. Operator: system entry or root.

One process per Keycloak instead: `kc-mcp.tool-prefix=prod_` renames tools (`prod_keycloak_user_search`);
`execute_tool` and config lists accept both spellings.
